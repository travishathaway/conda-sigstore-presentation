What is Sigstore?

Sigstore comprises several tools that can be used independently or combined for a comprehensive supply chain security solution. Sign your software without navigating tricky security protocols. Verify signatures against a tamper-proof log.

source: sigstore.dev
Motivate why Sigstore exists before defining it. The pain isn't cryptography — it's key management.

What problems does it solve?

  • Helps prevent the tampering of software artifacts
  • Traditional signing keys are difficult to manage securely
  • Signatures often lack trustworthy identity and auditability
Frame Sigstore as infrastructure, not a single tool — Cosign is just the CLI most people touch.
Photo from SHAN LU on Unsplash

Before Sigstore

  • Maintainer generates a keypair
  • Publishes, rotates, and protects the public key forever
  • Users must fetch & trust that key out-of-band

Example: Python releases <=3.13

  • Earlier Python releases relied on using OpenPGP keys
  • Each release manager was responsible for managing these public/private key pairs
  • This made release management more cumbersome and prone to error

Sigstore addresses these problems by helping users move away from a key-based signing approach to an identity-based one.

source: docs.sigstore.dev

With Sigstore

  • Maintainer proves identity via OIDC ("I am alice@example.com" or "I am this exact GitHub Actions workflow")
  • Gets an ephemeral keypair + short-lived cert
  • Signs, then discards the private key
  • Everything is logged publicly
No keys to manage, no keys to leak — that's the headline benefit.

"... the certificate authority"

  • Issues X.509 certs that bind an ephemeral public key to a verified identity — a human via OIDC login, or a machine identity (e.g. GitHub Action)
  • Valid OIDC providers: GitHub, GitLab, Google and Microsoft
  • Issuance itself is logged to a Certificate Transparency (RFC 6962) log
Fulcio is the piece that turns "I logged into GitHub/Google" into a cryptographic certificate a verifier can check.

"... the transparency log"

  • An append-only, publicly auditable, tamper-evident log of signing events (public good instance at rekor.sigstore.dev)
  • Every signature's existence becomes publicly observable, not just verifiable against a key
  • An inclusion proof lets anyone confirm an entry is really in the log without blindly trusting the log operator
Rekor is what makes short-lived certs safe to trust — anyone can audit who signed what and when.

Why transparency matters

  • Without a log, a compromised identity can be used for a targeted attack the public never sees
  • With a log, any use of an identity to sign something is discoverable in real time
  • Turns "silent targeted compromise" into "publicly detectable event"
This is the property CEP 27 explicitly calls out under "Transparency and auditability."

What's a software attestation?

  • An authenticated claim about a specific artifact
  • Adds context beyond just who signed it like where the source came from and where it was built
  • Typically machine-readable (e.g. JSON with schemas)
  • Provides evidence, not truth: attestations prove who created it and that it was not altered, not that the underlying claim is true

"... the attestation framework"

  • A framework/standard (in-toto.io) for defining machine-readable attestations
  • An attestation = a signed Statement made of a subject (what's being attested to — e.g. a file + its digest) and a predicate (arbitrary metadata about the subject, identified by a predicate type that defines its schema)
  • in-toto itself doesn't sign or provide transparency — it just defines the shape of the claim
in-toto is a data format, not a trust mechanism — that distinction sets up the next slide.

in-toto + Sigstore: two different jobs

  • The statement format (subject / predicate / predicate type)
  • A way to express arbitrary supply-chain claims (build provenance, publish events, SLSA, etc.)
  • The signing mechanism (ephemeral keys + Fulcio identity binding)
  • The transparency mechanism (Rekor)
  • The distributable container — a "Sigstore bundle" (cert + statement signature + inclusion proof)
in-toto answers "what are we claiming"; Sigstore answers "how do we trust who claimed it."

PEP 740

Index support for digital attestations

PyPI now accepts digital attestations on uploads, built on PEP 740 and the in-toto Attestation Framework

source: docs.pypi.org/attestations

PyPI is proof this isn't theoretical — it's already running in production for one of the largest package ecosystems.

What PyPI actually supports today

Predicate types

  • SLSA Provenance
  • PyPI Publish attestation
  • Max 2 attestations per file, no duplicate predicate types

Who can attest

  • Only Trusted Publisher identities: GitHub Actions, GitLab CI/CD, Google Cloud, ActiveState
  • Machine identities, not personal keys
Bridge to conda — CEP 27 explicitly cites PyPI/PEP 740 (and npm, RubyGems) as prior art.

CEP 27

Standardizing a publish attestation for the conda ecosystem

  • Defines in-toto statement and predicate type for the conda ecosystem
  • Includes information about the package + sha256 hash
  • Unlike PyPI, defines a predicate type that includes a targetChannel field
This is conda's own version of the PyPI Publish attestation from the previous slide.

The CEP 27 attestation shape


{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "7zip-26.03-hb0f4dca_0.conda",
      "digest": {
        "sha256": "bd861c...1f30d81833e7a62bc967ef9835248f4f40347"
      }
    }
  ],
  "predicateType": "https://schemas.conda.org/attestations-publish-1.schema.json",
  "predicate": {
    "targetChannel": "https://prefix.dev/github-releases"
  }
}
Note the direct parallel to PyPI's publish attestation — conda adds `targetChannel` because, unlike PyPI, there's no single canonical index.

CEP 27: sign & verify flow

Sign ✍️

  1. Generate ephemeral keypair
  2. Bind to identity via Fulcio cert
  3. Sign the in-toto statement
  4. Log to Rekor
  5. Produce a Sigstore bundle

Verify ✔ 🧾

  1. Fetch package + bundle
  2. Verify bundle against expected identity
  3. Check predicateType, subject name/digest, and (if present) targetChannel match
This is exactly the generic Sigstore flow from earlier slides, just instantiated with conda's specific predicate.

CEP 27's open question...
How do you get the bundle?

  • CEP 27 deliberately does not define a distribution mechanism for the bundles
  • Nor how clients establish trust in which identities to trust for a given package
  • Both are explicitly listed as future work...

Draft CEP: Distribution of Sigstore Attestations for Conda Packages

  • Proposes a mutable <package_url>.sigs sidecar endpoint returning a JSON array of Sigstore bundles for that package
  • Additionally, specifies an immutable content addressable URL: <package_url>.sigs.<hash>
  • A new repodata field lets clients detect when a package's attestations exist/change without an extra round trip per package
Stress that this is a moving target — field names and exact semantics are being actively revised in review.

Remember...

  • Sigstore only verifies who made a claim about an artifact and that it hasn't been tampered with
  • It makes absolutely no guarantees about the contents within it
  • Trusting the publishers of these artifacts is your job!
